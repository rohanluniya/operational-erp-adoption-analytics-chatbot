# Source Contract Review — CORE Pulse (`prototype.md` Baseline vs. Pilot Implementation)

This review records the three independent passes over `prototype.md` (Pass A: Semantics, Pass B: Data Model & Reliability, Pass C: Product Fit & Safe Extensions) and maps every baseline requirement to our **CORE Pulse** pilot (`SYNTHETIC DEMO DATA`).

| Baseline requirement (`prototype.md`) | Pilot implementation (`core-pulse`) | Extension / assumption / unresolved |
|---|---|---|
| **KPI 1 — Contracts Created:** `COUNT(DISTINCT ProjectId)` from `Project.Project` by `Project.CreatedDate`; never `ProjectStartDate` or `ProposedStartDate`. | Implemented verbatim in `silver.project`, `gold.coreadoption_event` (`PROJECT_CREATED`), `gold.coreadoption_kpi_daily`, and `goldview.v_core_adoption`. Projects and contracts represent the same population for this KPI. | None — exact match. Adversarial fixture `PRJ_FUTURE_START` (`CreatedDate` in Oct 2026, `ProjectStartDate` in Dec 2026) verifies creation-month bucket. |
| **KPI 2 — Employees Logging In:** `COUNT(DISTINCT APPUserId)` where `ApplicationLogType.Name = 'Application Login'` and `APPUser.IsServiceAccount = 0`, grouped at the requested period and scope by `ApplicationLog.CreatedDate`. Non-additive across dates, apps, entities, and waves. | Implemented verbatim in `silver.login_activity`, `gold.coreadoption_user_activity`, `gold.coreadoption_event` (`LOGIN`), and `goldview.v_core_adoption`. Every reporting level (`OVERALL`, `WAVE`, `ENTITY`) recomputes `COUNT(DISTINCT APPUserId)` directly; sums across child levels are blocked in both semantic code and guardrails. | `CURRENT` `OVERALL` reports cumulative distinct non-service users across the 18-month history (`All-time in dataset`), while ambiguous chat questions (*"How many users are using CORE?"*) default to **Current Month-to-Date (`Nov 2026 MTD`)** with explicit period labels (`SIMULATED EXTENSION` UX rule). Business label *"Employees"* uses `APPUserId` pending future HR roster linkage. |
| **KPI 3 — Timesheets Submitted:** `COUNT(DISTINCT TimecardId)` from `Timesheet.Timecard` where `SubmittedDate IS NOT NULL`, using `SubmittedDate` as event date regardless of later `Rejected`/`Approved`/`Exported` status; never `ProjectTask.ActualHours` or `ProjectTaskTimelineEvent`. | Implemented verbatim in `silver.timecard`, `gold.coreadoption_event` (`TIMECARD_SUBMITTED`), and `goldview.v_core_adoption`. `silver.task_activity` retains task hours separately and is never mixed into the timesheet KPI. | Timecards lack governed single-BU attribution (rows can span multiple project tasks/BUs); `BUSINESS_UNIT` rows are intentionally omitted for `Timesheets Submitted` and explained clearly in chat. |
| **KPI 4 — Expense Reports:** `COUNT(DISTINCT ExpenseReportId)` from `Expense.ExpenseReport` where `SubmittedDate IS NOT NULL`, using `SubmittedDate` as event date regardless of post-submission edits or workflow status changes. | Implemented verbatim in `silver.expense_report`, `gold.coreadoption_event` (`EXPENSE_SUBMISSION`), and `goldview.v_core_adoption`. | Default CORE `BusinessUnit` on `ExpenseReport` provides governed `BUSINESS_UNIT`, `ENTITY`, and `WAVE` attribution. |
| **Source systems & security (§4):** Original baseline references enterprise SQL Server linked server and `OP.APPUser` authentication columns (`Password`, `ConfirmationCode`, `SecurityCode`, `TwoFactorAuthenticationKey`). | Zero corporate connectivity. Replaced with deterministic synthetic `source_sim.*` tables (`SEED=42`, `AS_OF_DATE=2026-11-17`) for a fictional multi-region enterprise. Authentication secret columns do not exist in `source_sim.app_user` or `bronze.core_app_user`. | Intentional safety boundary: all schemas use neutral synthetic names; no proprietary server names appear in UI, SQL views, or exports. |
| **Medallion layers (§6–§8):** 16 Bronze `core_*` tables with `SourceExtractDateTime` & `PipelineRunId` (`ApplicationLog` bigint ID watermark); 10 Silver conformed tables (`LEFT JOIN` optional local org enrichment so unmapped CORE BUs are kept); Gold snapshot/user/event facts; single certified consumer view `goldview.v_core_adoption` + `goldview.v_dim_date`. | Implemented as real physical schemas and tables in **both SQL Server 2022 (`core_pulse` DB)** and **DuckDB (`data/core_pulse.duckdb`)**. All permanent inserts use explicit target column lists (`INSERT INTO schema.table (c1, c2, ...) SELECT ...`); a test rejects `INSERT ... SELECT *`. | Dual-backend support (`mssql` + `duckdb`) matches our proven IRIS platform architecture while keeping consumer queries pinned strictly to `goldview.v_core_adoption`. |
| **Attribution boundaries (§6.4, §7.3, §8):** Logins have no reliable BU mapping; Timecards lack single-BU allocation; `silver.application_mapping` maps `ApplicationCode -> AdoptionEntity, AdoptionWaveNumber, MappingStatus` (`CONFIRMED`, `REVIEW`, `EXCLUDED`). | Enforced strictly: `goldview.v_core_adoption` publishes `BUSINESS_UNIT` rows **only** for `Contracts Created` and `Expense Reports`. Asking for `Employees Logging In` or `Timesheets Submitted` by BU returns an explicit governance explanation rather than fabricated numbers. | Persona Row-Level Security (`rls.fn_core_access` on SQL Server + Python filter on DuckDB) scopes regional personas (`AMER`, `EMEA`) cleanly while preserving global non-additive semantics for `Global CORE Program Lead`. |
| **DataOps & validation (§10–§11):** `dataops.pipeline_registry`, `pipeline_run`, `pipeline_step_run`, `watermark`, `data_quality_metric`; statuses `RUNNING`, `SUCCESS`, `WARNING`, `FAILED`, `CANCELLED`; source-to-event parity, referential orphan detection, freshness checks. | Implemented in `pipelines/medallion.py` and `sql/`. Reruns are idempotent (staging before swap; watermark advances only after commit). SQL Server DDL includes `SET XACT_ABORT ON` and safe rollback-before-logging patterns. | Orphans, duplicate staging rows, late-arriving logs, and `REVIEW`/`EXCLUDED` app mappings are injected via deterministic fixtures and surfaced in `dataops.data_quality_metric` and the Data Catalog. |
| **Rollout & Module Go-Live Registry (Pass C gap):** Baseline `prototype.md` maps applications to entities/waves (`silver.application_mapping`) but lacks an authoritative business/module go-live registry or eligible headcount denominator. | Added `reference.module_catalog` and `reference.rollout_registry` (`PLANNED`, `ONBOARDING`, `LIVE`, `PAUSED`, `RETIRED`), explicitly badged `SIMULATED EXTENSION` in UI, Catalog, and tool payloads. | Distinguishes (1) configured rollout status, (2) optional `EligiblePopulation`, (3) app logins, and (4) instrumented module transactions (`NOT INSTRUMENTED` modules like Scheduling, Qualifications, Lab Testing, Invoicing are never inferred from logins). |
| **Application & AI Stack (User Override):** Prompt draft suggested React/FastAPI/OpenAI cloud API; `prototype.md` §15 outlined read-only MCP resources/tools. | Aligned 100% with the IRIS production-grade prototype stack per stakeholder direction: **Streamlit UI** (`Chat`, `Rollout Explorer`, `Data Catalog`, `User Guide`, `About`), **LiteLLM -> GKE Ollama (`gpt-oss:20b`, `qwen2.5-coder:14b`) + offline `rules` mode**, **SQL Server 2022 + DuckDB**, **10-conversation user history**, **Numeric & Non-Additivity Guardrail**, plus the **read-only Python MCP Server (`mcp_server/server.py`)** sharing the exact governed semantic functions. | Zero external data egress; identical UX, sign-in (`APP_ACCESS_CODE`), sidebar filters, context memory, and executive presentation assets as IRIS. |
